Shopping Cart MCP Server

Technical specification for exposing the shopping-cart microservices to LLMs through the Model Context Protocol, with authenticated users, a real cart, and a safe checkout.

The idea in one analogy

Think of a restaurant. The LLM is the customer, the backend services are the kitchen, and the MCP server is the waiter. The customer can only order what is on the menu (the tools), the waiter checks who is sitting at the table (OAuth token), and the waiter never lets the customer walk into the kitchen or name their own price.

Goals

In scope

Search products, manage a cart, check out, track order status. OAuth 2.1 login via a demo Spring Security auth server. One remote MCP server, ChatGPT as first client, adapters for Claude and Gemini after.

Out of scope

Real payments (the credit-limit approval flow stands in), admin catalog tools, multi-tenant stores, inventory reservation across warehouses.

Teaching value

Shows each MCP concept end to end: tools with schemas, annotations, resource-server auth, structured results, and human confirmation for risky actions.

Responsibilities

ComponentResponsibility

GatewayReplaces end-of-life Zuul. Validates JWT again, forwards X-Customer-Id from the token, rate limits per user

Order / CustomerOrder creation from a cart, Kafka credit check, status updates, as today but with fixes below

Security and trust

Authentication flow

sequenceDiagram
participant U as User
participant C as ChatGPT
participant M as MCP Server
participant A as Auth Server
C->>M: POST /mcp without token
M-->>C: 401 with protected resource metadata
C->>A: Discover, register client, start PKCE flow
A->>U: Login and consent for scopes
U-->>A: Approve
A-->>C: Access token (JWT, audience = MCP server)
C->>M: tools/call with bearer token
M->>M: Validate JWT, map sub to customerId

Scopes: cart:read, cart:write, orders:read, orders:write (checkout). Tokens live 15 minutes; refresh tokens are optional for the demo. The MCP server must not forward the user’s token to other services unchanged; it exchanges or re-issues a downstream token with the right audience.

Threats and controls

ThreatControl
Model or user supplies a fake price or another customer’s IDPrices and customer come only from the server and the token; tools have no such inputs
Order placed without user intent (prompt injection, model error)Two-step checkout, destructiveHint, cap on order total and on items per cart
Prompt injection through product textTreat tool output as untrusted data: strip markup, length limits, structured JSON only
Duplicate order on retryIdempotency key = cart ID + cart version; stale versions are rejected
Access to other users’ carts or ordersAll queries filtered by token sub; integration tests for cross-user access
Abuse or runaway tool loopsPer-user rate limits at the gateway, quantity limits in tool schemas
Leaked secretsRemove docker/aws-ec2 private key from the repo and git history, rotate it if it was ever used, move credentials to environment variables

Why Gemini gets its own schema profile

Gemini function declarations accept an OpenAPI-style subset of JSON Schema, and unsupported keywords can fail a whole request with a generic 400. The gemini profile removes anyOf, pattern, numeric bounds, defaults and titles from the published schema and moves limits into each parameter’s description (for example “Allowed: 1 to 10”). The standard profile keeps the full schema.

The profile is chosen by the X-Client-Profile header, then the MCP client name, then the CLIENT_PROFILE setting. shopping-cart-compat-check shows what a client sees and flags incompatibilities.

Not yet verified live: the Claude and Gemini connection snippets in the repo’s examples/ folder follow the vendors’ current documentation but were not run against their live APIs. The Gemini details come from Google announcements and third-party docs, so check Google’s Interactions API reference before relying on exact field names. The Spring authorization server must support dynamic client registration for the Claude connector flow.
